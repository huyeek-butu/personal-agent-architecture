# Agent 系统架构与运行机制 · 实况记录

**中文** ｜ [English](README.en.md)

> 一份把 **AI agent 当作可维护系统** 来做的实况记录 —— 底座是给定的（桌面端 agent 运行时），上层是自建的（8 层规则自治理体系）。两层之间只有一个咬合点，所有设计权衡都从那里长出来。

这不是理论文章，也不是产品文档。它记录的是**一台真实在跑的机器**：跑了几百轮对话、几十次任务、二十多轮自我复核之后，长成什么样、哪里断了、哪里是拿一个换另一个换来的。

---

## 三个非常识的结论

如果只读三句话，读这三句：

1. **规则写在哪里，比规则写什么更重要。** 每轮被注入的规则**一定**会被执行（但吃掉上下文预算）；按需加载的规则只能靠"想起来才查"，**失效时不报错**。所以"外移"如果只写一句"详见 xxx"、把动作句搬走了，等于把强制执行的规则降级成自觉执行 —— 这是静默流失。

2. **四个咬合点的强弱是不对称的。** 注入点（平台强制）> 脚本校验（可复现）> 路由表（可能不查）> 外部复核（通道常缺席）。所以真正的主线动作只有一件事：**把规则从"路由"往"脚本"搬** —— 能写成 lint 的就别写成话。

3. **单 agent 架构有天花板。** 整套系统的可靠性，有相当一部分压在"模型自己判断得准"上（这算不算新任务、这算不算大改动）。规则能降低误判率，但消不掉 —— 因为执行判断的就是它自己。

## 三级标注

全文每个事实都带一个来源等级，不放任推断和确知混在一起：

| 标注 | 含义 |
|---|---|
| **✅ 确知** | 有文件、有命令输出、有实测行为可直接指认 |
| **○ 推断** | 从外部可观测行为反推，看不到实现，可能错 |
| **✗ 不可见** | 平台内核，没有任何观测通道 |

读的时候建议先看标注 —— 本文最有价值的部分，恰恰是那些标了 `✗` 的地方：**明确承认哪里看不到**。

## 它不是什么

- **不是官方文档。** 与所运行的平台方无关，纯属使用者视角的实测记录。
- **不是最佳实践。** 六处权衡都是"在特定约束下选了 A、牺牲了 B"，换个约束（团队规模、成本预算、合规要求）结论会变。
- **不是可复制的配置。** 8 层规则的具体内容与具体场景强绑定；可迁移的是**结构与方法**，不是条目。

---

## 适用场景

如果你也在做这几件事，这篇可能有参考价值：

- 长期（几个月以上）跟同一个 agent 协作，规则越加越多、开始互相打架
- 想让 agent 的行为**稳定可预期**，而不是每次看运气
- 需要让 agent **自己审自己**，又知道自评不可靠
- 关心"规则体系怎么不腐化"这类元问题
